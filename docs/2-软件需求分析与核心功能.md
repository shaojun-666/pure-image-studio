# 软件需求分析与核心功能

**项目名称**：Pure · AI 图像工作室（多模型 AI 生图工作台）
**项目形态**：可公网访问的 Web 应用（自购云服务器部署）
**技术栈**：Next.js 15 + React 19 + TypeScript + PostgreSQL + Prisma 7
**开发方式**：单人开发，全程使用 AI 编程工具（Claude Code）
**开发周期**：2026 年 9 月 14 日 — 9 月 21 日

---

## 一、项目概述

### 1.1 项目背景

AI 生图已经从"玩具"变成了真实的生产力工具，但目前主流的生图产品对中文用户存在几个明显的摩擦点：

1. **模型分散**。豆包 Seedream、通义千问、Gemini、GPT-Image 各有擅长，用户要在多个平台之间来回切换、各自充值、各自管理历史记录。
2. **中文提示词门槛高**。多数产品的提示词工程知识门槛不低，"文生图"到"出好图"之间隔着大量试错。
3. **系列图的人物一致性差**。这是最痛的一点：想让同一个角色出现在多张图里（漫画分镜、产品代言人、连载插画），现有产品普遍做不到，每次生成出来的人物长相都会漂移。
4. **计费不透明**。用户很难搞清楚一次生成到底扣了多少、为什么扣、失败了退不退。

本项目针对以上四点，构建一个**多模型聚合、中文友好、以"形象一致性"为核心卖点**的 AI 生图工作台。

### 1.2 项目定位

一个面向中文用户的**专业级 AI 图像创作工作台**。它不追求"一句话出图"的玩具体验，而是提供一个完整的创作闭环：

> 选模型 → 写提示词（可 AI 润色）→ 选风格与画幅 → 引用形象 → 批量生成 → 管理历史/收藏/集合 → 分享到作品广场

### 1.3 目标用户与典型场景

| 用户类型 | 典型场景 | 核心诉求 |
|---|---|---|
| 内容创作者 | 为文章/视频批量配图 | 批量生成、风格统一、历史可复现 |
| 插画/漫画作者 | 连载作品中保持角色一致 | **"形象"功能**（本项目核心卖点） |
| 电商运营 | 商品图换背景、扩图、去物体 | 图像编辑类工具 |
| 普通尝鲜用户 | 试玩不同模型的效果差异 | 免费额度、模型对比、作品广场 |

### 1.4 术语约定

- **积分（Credits）**：站内计费单位。不同模型、不同生成模式消耗不同。
- **形象（Character）**：用户自建的虚拟角色，由"外形描述"和/或"参考图"构成，在提示词中用 `@[名字]` 引用。
- **集锦（Collection）**：用户对生成结果的自主分组。
- **能力门控（Capability Gating）**：界面控件根据所选模型的能力动态启用/置灰，而非无条件可选。

## 二、需求分析

### 2.1 用户角色

| 角色 | 权限 |
|---|---|
| **游客** | 浏览首页、作品广场、定价页、静态页面；可使用 6 个图像处理工具中的公开部分；**不可提交生成任务**（尝试时弹窗引导登录） |
| **注册用户** | 全部生成功能、提示词助手、历史记录、收藏、集锦、形象管理、积分面板、个人风格 |
| **管理员** | 上述全部 + 后台：用户管理、积分发放、生成记录管理、模型上下架、风格/提示词/广场内容编排 |

### 2.2 功能性需求

#### FR-1 账号与鉴权
- 邮箱 + 密码注册/登录，密码使用 bcrypt 单向哈希存储。
- 注册即赠送积分（默认 30）。
- 会话基于 Auth.js v5（JWT 策略），支持服务端与客户端两种取用方式。
- 未登录用户点击生成时，以弹窗形式提示登录，而非静默失败。

#### FR-2 图像生成（8 种模式）

| 模式 | 说明 | 是否需要底图 |
|---|---|---|
| 文生图 | 纯提示词出图 | 否 |
| 图生图 | 以一张图为起点重绘 | 是 |
| 局部重绘 | 涂抹区域后重绘该区域 | 是 + 蒙版 |
| 扩图 | 向画布外扩展内容 | 是 |
| 抠图 | 移除背景 | 是 |
| 放大增强 | 提升分辨率与细节 | 是 |
| 风格迁移 | 把参考图的风格套用到目标图 | 是 + 风格参考图 |
| 对象消除 | 抹掉指定物体 | 是 + 蒙版 |

配套能力：
- **画幅**：8 种（1:1 / 4:3 / 3:4 / 16:9 / 9:16 / 21:9 / 3:2 / 2:3）
- **分辨率**：1K / 2K / 4K（视模型能力而定）
- **批量生成**：一次最多 8 张
- **随机种子与引导强度**：可复现、可微调（视模型能力而定）
- **生成过程实时反馈**：通过 SSE 推送状态、逐张出图、失败原因
- **任务取消**：未开始的任务可取消并全额退款

#### FR-3 提示词助手
- **AI 润色**：调用文本模型把口语化描述改写为结构化生图提示词。
- **中英翻译**：适配以英文提示词效果更好的模型。
- **随机提示词**：给没有灵感的用户一个起点。
- **预设提示词库**：后台可维护的提示词模板，用户一键套用。

#### FR-4 形象（Character）——本项目核心创新
- 用户可创建、重命名、删除自己的形象，数据隔离在个人账户下。
- **两种形态**：文字形象（仅外形描述）与图片形象（外观描述 + 参考图）。
- **创建来源**：上传新图，或**直接复用历史生成中的某一张图**（复用存储、不复制字节）。
- **引用方式**：在提示词输入框敲 `@` 唤起选择列表，选中后高亮显示，可随时切换。
- **落库策略**：生成记录保存用户输入的原文（含 `@[名字]`）以便回显与"同款"复用；真正发给模型的是注入展开后的版本；同时保存提交时刻的形象快照，保证之后改名不影响历史记录。
- **能力适配**：模型支持"形象参考图"时，除文字描述外还会把参考图一并递给模型；不支持时**静默降级**为纯描述注入，不报错。

#### FR-5 历史、收藏与集锦
- **历史记录**：分页列表 + 单条详情（完整参数、结果图、原始提示词），支持"一键同款"复现。
- **收藏**：对单张图切换收藏状态。
- **集锦**：用户自建分组，批量加图/移出；集锦封面与计数自动重算。

#### FR-6 作品广场
- 公开只读的作品流，支持分类、精选、浏览量统计。
- **一键同款**：把作品的提示词与参数回填到生成器。

#### FR-7 积分体系
- **获取**：注册赠送、每日免费额度、后台手动发放。
- **消耗**：按 `模型单价 × 模式倍率` 计算单张成本（最低 1 分）。
- **透明**：完整流水可查，每笔显示变动值与变动后余额。
- **退款**：生成失败或部分失败，未成功的张数自动退款。

#### FR-8 多模型接入与能力门控
- 已接入 **3 家真实厂商 / 12 个可用模型**，另有 3 个仅供测试的 mock 模型。

| 厂商 | 模型数 | 代表模型 | 特点 |
|---|---|---|---|
| 阿里云百炼 | 4 | Z-Image-Turbo（3 分）、Qwen-Image 3.0（默认）、Qwen-Image-Edit-Max | 中文语义好，编辑能力强 |
| 火山引擎方舟 | 4 | 豆包 Seedream 4.0 / 4.5 / 5.0 / 5.0 Pro | 人物一致性强，全部支持形象参考 |
| ofox.ai 中转站 | 4 | Nano Banana Pro、GPT Image 2 等 | 覆盖海外主流模型 |
| mock（仅测试） | 3 | — | 端到端验收用，用户不可见 |

- **能力门控**：前端的画幅、分辨率、批量数、模式开关、能否选图片形象，**全部由后端返回的能力描述驱动**。不支持的能力在界面上置灰并给出原因，而不是让用户点了再报错。
- **未配密钥的厂商不注册**：不会出现"点了必然失败"的模型按钮。

#### FR-9 管理后台
- 仪表盘：用户数、生成量、积分数等运营指标。
- 用户管理：查看用户、调整状态、**手动发放积分**。
- 生成管理：查看全站生成记录、重排失败任务。
- 模型管理：上下架、排序、价格覆盖、徽章文案。
- 内容管理：风格预设、提示词预设、广场作品的增删改与拖拽排序。

#### FR-10 国际化
- 支持中文（默认）与英文，路径始终带语言前缀。
- 界面文案共约 900 条/语言，一一对应。
- 数据库层面：模型名、风格名、提示词标题等多语言字段以 JSON 存储；**提示词正文与作品提示词不翻译**（它们是用户要复制走的产物）。

### 2.3 非功能性需求

| 类别 | 需求 | 实现要点 |
|---|---|---|
| **正确性（最高优先级）** | 积分账目绝不允许出错 | 流水表追加写、余额缓存可对账修复、全链路幂等键、行锁串行化 |

| **成本可控** | 生图是真实开销 | 能力实测优先用零成本方式探测、免费模型承担示例图生产、失败即退款 |
| **易用性** | 中文用户零学习成本 | 全中文界面、提示词助手、预设风格与提示词库 |

## 三、核心功能详解

### 3.1 多模型工作台与"能力门控"

**问题**：不同生图模型的输入输出约束差异极大。有的只接受文字，有的必须给底图，有的有总像素下限，有的不支持反向提示词，有的不接受随机种子。如果界面无条件提供所有选项，用户会频繁撞上"点了就报错"。

**方案**：把"能力"抽象成一份结构化描述（支持哪些模式、最多几张参考图、参考图能扮演什么角色、支持哪些画幅与分辨率、是否支持蒙版/强度/种子/引导、提示词长度上限、是否异步、典型耗时）。这份描述由各厂商适配层声明，经接口下发给前端，**前端所有控件的可用性都由它驱动**。

**效果**：新增模型时前端一行代码都不用改，界面自动适配。例如方舟的 Seedream 4.5 与 5.0 因总像素下限较高而不提供 1K 档，界面上 1K 会自动置灰。

### 3.2 "形象"：让同一个角色在多张图里长得一样

这是本项目针对行业痛点的核心设计。

**用户视角**：创建一个形象（写外形描述、可选传一张参考图）→ 生成时在提示词里敲 `@` 引用 → 该角色就会以稳定的长相出现在新图里。

**实现上的三个关键决策**：

1. **两种形象，一个判据**。文字形象只靠描述注入，任何模型都能用；图片形象在此之上还会把参考图递给模型。区分二者的方式**不是**新增一个类型字段，而是"有没有绑定图片资源"——避免类型字段与实际状态不一致的"双真源"问题。

2. **降级是设计的一部分**。模型不支持形象参考图时不报错，而是只走描述注入。用户在任何模型上都能使用形象功能，只是效果强弱不同。

3. **参考图槽位要自己算**。厂商的参考图上限是所有非底图类参考图**共用**的，而风格迁移本身已经占了一格。如果不预先扣除，会出现"用户多选了几个形象 → 超出上限 → 提交直接被拒"的糟糕体验。因此服务端会先算清可用槽位，超出的形象**只注入描述、不报错**。

**能力的实测纪律**：一个模型是否真的"能读懂参考图并把人物长相带过去"，必须用真实调用验证 —— 用一个**无法从提示词猜出长相**的参考主体，提示词中完全不描述长相，看输出是否稳定还原。只有通过验证的模型才会在界面上开放"图片形象"。当前方舟的 4 个 Seedream 型号与百炼的 Qwen-Image-Edit-Max 已通过验证；ofox 全线未通过，因此不开放。

### 3.3 积分账本：一套可自审计的计费系统

**设计原则：账本是唯一真相，余额只是缓存。**

- **流水表只追加，永不修改、永不删除**。每一笔都记录变动值与该笔发生后的余额快照。因此账本本身就是完整的审计轨迹，任何时点的余额都能被独立复原。
- **退款不是"撤销"，而是追加一笔补偿**。一次 40 分的生成最终只成功 2 张，账本上看到的是"冻结 -40 → 退款 +32"，一眼看得懂，而不是原记录被悄悄改掉。
- **全链路幂等**。冻结、结算、退款、发放、对账修正，每一类操作都有唯一幂等键。重复请求不会重复扣费。
- **每日自动对账**。定时任务逐用户比对"流水累计值"与"余额缓存"，发现漂移**不静默改数**，而是补一条修正流水留痕后再修正缓存。
- **后台发放与审计同事务**。管理员发积分与写入审计日志在同一个数据库事务里完成 —— "钱发出去了但没人知道是谁发的"是后台最不该出现的事。
- **钱包操作串行化**。同一用户的并发扣费通过数据库行锁串行执行，杜绝并发下的余额穿透。

### 3.4 生成任务的完整生命周期

```
提交 → 校验能力与余额 → 【冻结积分】→ 落库 → 派发厂商 → 轮询/等待
     → 逐张落图 → 【结算：扣实际消耗、退未成功部分】→ 完成
                ↘ 取消/失败 → 【全额退款】
```

要点：
- **冻结与落库在同一事务**：不会出现"钱扣了但没有任务"或"任务在跑但没扣钱"。
- **幂等键防重复提交**：网络重试不会造成重复扣费。
- **失败分类决定重试还是退款**：认证失败、内容审核命中属于"重试无用"，立即退款；限流、上游故障属可重试，走退避重试。
- **取消是原子抢占**：只有尚未开始的任务能取消，通过带状态条件的批量更新实现原子性，避免与派发流程竞争。

### 3.5 厂商抽象层：一个文件接入一家厂商

**目标**：把"接入新厂商"的成本压缩到最小。

**结构**：每个厂商一个文件，内含该厂商的模型目录、能力声明、HTTP 调用与错误映射。新增一家厂商的完整改动是**新增一个文件 + 在注册表加一行**。

**统一契约**：所有厂商都实现同一个接口，向上层屏蔽同步/异步、轮询/回调、base64/URL 返回等差异。上层（任务编排、计费、落库）完全不知道下游是哪一家。

**能力实测的落点**：能力声明不是照文档抄的，而是逐项实测后写死的白名单。例如"某厂商不支持蒙版"这一条，是通过对比蒙版内外像素差异发现的（差异几乎为零 → 说明蒙版被丢弃、实际是整图重绘）——这类"接口返回 200 但语义被静默忽略"的情况，只有实测才能发现。

### 3.6 后台与运维闭环

- **审计**：所有后台写操作记录操作人、动作、目标对象、变更内容、IP。
- **对账**：每日定时比对账本与余额缓存。
- **备份**：每日定时数据库备份，并配套恢复验证脚本。
- **鉴权**：定时任务不走用户会话，而是用共享密钥并采用定长比较，防止时序侧信道；生产环境该密钥为必填项。

│  ┌──────────────┬──────────────┬──────────────────┐ │
│  │ 认证与鉴权    │ 生成任务编排  │  积分账务         │ │
│  │ (Auth.js v5) │ (create/exec)│  (冻结/结算/退款) │ │
│  └──────────────┴──────┬───────┴──────────────────┘ │

### 4.2 数据模型（19 张表）

| 分组 | 表 | 作用 |
|---|---|---|
| 用户与认证 | User / Account / Session / VerificationToken / PasswordResetToken | 用户主表与认证适配表 |
| 目录 | ModelRegistry / StylePreset / PromptPreset | 模型、风格、提示词三类可运营数据 |
| 创作 | Generation / GenerationImage / Asset | 生成任务、结果图、用户素材 |
| 形象 | Character | 用户自建形象 |
| 积分 | CreditLedger / DailyGrant / AdminAuditLog | 流水、每日额度、后台审计 |
| 组织 | Favorite / Collection / CollectionItem / ExplorePost | 收藏、集锦、作品广场 |

**几个值得说明的字段设计**：

- `User.creditBalance` 注释明确写着"余额缓存，真相在 CreditLedger"——从命名上就杜绝后来者误把它当真源。
- `CreditLedger.idempotencyKey` 唯一约束，是整套幂等机制的**唯一依靠**。
- `DailyGrant` 对「用户 + 日期」建唯一约束，使"每日额度不累积"成为**结构性保证**而非业务逻辑约定。
- `Character` 对「用户 + 名字」建唯一约束——因为 `@[名字]` 反查依赖它去歧义，这是功能正确性的一部分，不只是数据整洁。
- `Generation` 把输入、执行、**资金**、运维四类字段分区存放，其中资金区独立记录"冻结/已扣/已退"三个数，与流水表互为印证。

### 4.3 关键技术决策

| 决策 | 理由 |
|---|---|
| 用 PostgreSQL 而非 SQLite | 需要行级锁做钱包串行化、需要时区感知的日期分桶做统计、需要生产级备份 |
| 账本追加写 + 余额缓存 | 兼顾可审计性与读取性能；漂移可自动检测与修复 |
| 能力描述由服务端下发 | 前端零改动适配新模型，且能力约束不会被前端绕过 |
| 提示词原文与展开版分开存 | 前者供用户回看与复用，后者是真正发给模型的文本，用于排查问题 |
| 存储 key 复用而非复制字节 | 从历史生成创建形象时不产生冗余存储 |
| 非本人资源返回 404 而非 403 | 避免通过状态码探测资源是否存在 |

## 五、实现现状与已知局限

项目已完整实现上述功能并部署上线，但以下边界**尚未打通**，在此如实列出，避免过度声明：

1. **抠图与放大增强对真实模型不可用**。这两项模式仅在测试用的 mock 模型中开启，三家真实厂商均未开放，用户在真实模型下会看到对应工具被置灰。
2. **局部重绘与对象消除不可用**。实测发现所用中转站会静默丢弃蒙版（返回成功但实际是整图重绘），因此未对用户开放。
3. **扩图仅有部分模型支持**，且实现方式为服务端预扩画布 + 提示词引导，并非厂商原生扩图接口。
4. **方舟 4 个模型的积分定价为占位值**，待按厂商实际单价校准。
5. **4K 分辨率未经验证**，因此未在任何模型上声明。
6. **素材自动清理未实现**。数据结构中已预留过期时间字段与清理注意事项，但 GC 逻辑尚未编写。
7. **无自助找回/修改密码入口**，密码为单向哈希，遗失后只能由管理员重置。
8. **博客、常见问题、使用教程、隐私政策、服务条款为占位页**。

## 六、后续规划

1. **补齐图像编辑能力**：寻找支持蒙版的厂商，打通局部重绘与对象消除。
2. **定价校准**：按厂商实际单价重算全部模型的积分梯度。
3. **形象能力的横向扩展**：随着新模型接入，持续做参考图能力实测，扩大支持形象参考的模型范围。
4. **多形象与场景一致性**：支持在同一张图中引用多个形象（当前已支持至 3 个），并研究跨场景的长期一致性。
5. **团队协作**：形象的共享与导出。
